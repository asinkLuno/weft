# Weft 实体关系：归属层级与两两关系

第一遍建完实体后搭它们之间的结构。两种机制，判断口诀：

- 能问「**X 是 Y 的成员/一部分**」→ 层级归属，写 `belong_to`（人物属于学院、成员属于家族）。
- 只能问「**X 和 Y 之间是什么关系**」→ 平级两两关系，写 `entity_link`（母子、朋友、敌对、师生）。

## belong_to：归属层级

```yaml
entity:
  霍格沃茨魔法学校:
    description: 英国的魔法学校。       # 根：不写 belong_to
  格兰芬多:
    belong_to: [霍格沃茨魔法学校]
  阿不思·邓布利多:
    belong_to: [格兰芬多, 霍格沃茨魔法学校]   # 多父合法：既属学院又直属学校
```

规则：

- 值是上级实体 id 列表；引用必须存在（`EntityUnknownParent`），**不许成环**（`EntityCycle`，整份文档构建失败）。
- 多父合法——归属是 DAG 不是树；重复边自动合并，输出按 id 排序去重。
- 无上级的实体自成树根；**多棵树并存是常态**（示例中「德思礼一家」「伏地魔」都是独立根）。不是所有实体都要挂进一棵树，孤立实体（只被事件引用）完全合法。
- 血缘与抚养是两个容器，多父正是为此存在：寄养的孩子既挂血缘家庭也可挂抚养家庭。
- 常驻成员（驻学院的幽灵、宠物、球队队员）挂 `belong_to`；一次性互动（救命之恩、买卖）走 `entity_link`。同一份文档里同类情况保持同一口径。
- 历史从属（某人曾就读某学院）仅在文本明确陈述时挂 `belong_to`；只作传闻、暗示或背景介绍的写进 description，不要靠外部知识补。
- 归属在输出侧由顶层 `belong_dag` 统一表达（构建期反查生成）；写作时只管在实体上写 `belong_to`，不要自己发明 `belong_dag` 键。

## entity_link：两两关系

按组组织，每组一批关系对；`entities` **恰好两个** id（多写少写都反序列化失败），`relations` 是自由文本：

```yaml
entity_link:
  波特一家:
    - entities: [哈利·波特, 莉莉·波特]
      relations: 母子
    - entities: [莉莉·波特, 詹姆·波特]
      relations: 夫妻
  格兰芬多伙伴:
    - entities: [哈利·波特, 罗恩·韦斯莱]
      relations: 同学与朋友
    - entities: [哈利·波特, 赫敏·格兰杰]
      relations: 同学与朋友
```

- 组名是自由命名的人为分组（按家族、按朋友圈、按阵营），仅用于归类展示。
- 只校验两端 id 存在（`UnknownLinkEntity`）；`relations` 不做语义处理，写读者能懂的话即可。
- 三人互为朋友 = 三对，逐对写全。

## 第一遍的搭法

1. 先找**容器**：学校、家族、势力、团队——建为实体、不写 `belong_to`，作为树根。
2. 把成员逐个挂上去（`belong_to: [容器]`）；有多重身份就写多父列表。
3. 平级关系（亲属、友谊、敌对）单独收集，按主题分组写成 `entity_link`。
4. 成对行动的角色（孪生兄弟、双人组）**各建一张单人卡**，用 `entity_link` 表达孪生/搭档关系，不要合并建卡。
5. 挂不进任何树的实体不必硬挂，留给事件引用即可。

分批提取（比如按章节分人读）时，第一遍结束先做一次**归一**：合并各批名单、统一同一实体的叫法（容器名、别名选一个）、把各批分别建出的同一对象合成一个 id——事件参与者全靠这套 id，归一不干净后面全是断引。

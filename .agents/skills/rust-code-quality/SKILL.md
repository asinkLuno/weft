# 编写易维护的 Rust

依据 [Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html) 提炼通用原则。优先遵循当前项目约定、官方 Rust 风格与 API 指南；原文中标明 Chromium、Fuchsia、Android 等平台的规则只适用于相应代码库。以长期可读性、清晰的契约和必要的性能为目标。库的公开 API 要考虑不同调用方；应用内部代码优先直接、简单，避免过早抽象。

## 设计与实现

- **所有权表达真实关系。** 优先独占所有权与借用。不可变参数尽量接收 `&str`、`&[T]`、`&T` 或 `Option<&T>`，避免要求调用方持有特定容器。不要用深度 `clone()` 回避本可清晰表达的借用；借用关系过于复杂时，可以权衡复制。只有共享所有权确有必要时才引入 `Rc` 或 `Arc`。
- **让 API 说清意图。** 含义不明显的布尔参数用 `enum`；语义不同或容易混淆的值用 newtype；字段有业务含义时用命名结构体。可复用库若只需遍历输入，可考虑 `IntoIterator`，若可延迟产出，可考虑返回迭代器；应用代码中 `&[T]` 与 `Vec<T>` 往往更直观。`impl Into<T>` 只用于调用方便足以抵偿泛型复杂度的库 API。
- **按失败性质选类型。** 缺失等原因显而易见的正常结果用 `Option`；调用方需要失败原因并可能恢复时用 `Result`；违反程序不变量才 panic。用模式匹配处理 `Option` 与 `Result`，避免先检查再 `unwrap()`。不变量确实需要 panic 时，用 `expect()` 说明原因。
- **控制抽象成本。** 方法符合标准 trait 语义时实现该 trait；能 `derive` 时不要手写。trait 应服务于泛型、动态分发或扩展外部类型，不要仅为整理代码而建。库中泛型与 `dyn Trait` 的选择要考虑调用灵活性、代码体积及分发成本。优先普通函数和类型；宏只用于普通 Rust 难以清楚表达的重复结构。
- **让实现容易读。** 复杂类型推断处标注类型；迭代器链若隐藏分支或副作用，改用 `for` 和 `match`；短链能清楚表达 `any`、`map` 等意图时保留。导入保持来源可辨，避免无差别 glob 导入。使用项目的 `rustfmt` 设置，不为个人偏好跳过格式化。
- **维护公开契约。** 公共 API 文档说明行为、重要约束与可能的 panic；`unsafe` 必须有必要性，并用 `SAFETY:` 注释解释其成立条件，尽量封装在安全接口内。公开类型考虑向后兼容，但不要机械添加 `#[non_exhaustive]`、`#[must_use]` 或 `const`；根据实际调用方式和承诺决定。

审查时指出具体代码位置、读者或调用方会遇到的问题，以及最小可行改法。区分明确的正确性问题与可商量的风格选择。
